std::copy가 출력 범위의 끝을 받지 않는다 → src.size()만 키워 dest 버퍼를 선형으로 넘침 → 0x20 뒤에 붙어 있는 Menu 객체의 함수 포인터를 getshell로 교체.

Vulnerability & Code Analysis

보호기법 값 이 경로에 미치는 영향
PIE No PIE (0x400000 고정) getshell 주소 고정 → leak 불필요
RELRO Partial GOT를 쓰지 않음 → 무관
NX on 기존 코드로 점프 → 무관
Canary found 스택을 건드리지 않음 → 무관

checksec만 보면 “카나리 leak → ROP”로 읽히지만, 이 문제는 스택 버퍼를 아예 쓰지 않는다. char buf[]가 없고 입력은 전부 std::cin >> int로 받아 힙에 있는 vector 로 들어간다. 카나리는 지나갈 일이 없는 문 앞의 알람이다.

메뉴 구조

취약점

입력 지점 중 값이 아니라 크기를 받는 곳이 하나 있다.

resize 자체는 안전하다. vector는 숫자와 실제 버퍼를 항상 같이 갱신하므로 혼자서는 절대 넘치지 않는다. 다만 src.size()와 dest.size()를 서로 다르게 만들어 둘 수 있는 상태를 남긴다.

그 상태를 터뜨리는 코드가 메뉴 3번이다.

인자를 세어보면 출력 범위의 끝이 없다. std::copy의 3-인자 버전은 입력 범위 [first, last)와 출력 시작점만 받고, 담을 자리가 있는지는 호출자가 보장하라는 계약이다. 그 보장 코드가 이 함수에도, 호출하는 main에도 없다.

memcpy(dst, src, src_len) 과 논리적으로 동일한 버그다. 길이를 source가 정하고 destination의 용량을 확인하지 않는다.

능력

= 선형 힙 오버플로우. 메뉴를 공격자 언어로 번역하면 이렇게 된다.

메뉴 역할
2. modify 쓸 개수를 정한다 (src.resize)
1. make 쓸 값을 정한다 (cin >> data)
3. copy 방아쇠를 당긴다

Exploit / Solver Strategy

1. 타겟 — RIP는 어디서 오나

main은 while(1) 무한 루프라 리턴할 일이 없다. 리턴 주소 덮기는 길이 아니다.

CPU가 점프하는 순간은 call/jmp/ret 셋뿐이고, 그중 점프 주소를 메모리에서 읽어오는 것만 조작 가능하다. 후보는 셋이다.

후보 사는 곳 힙 쓰기로 닿나
리턴 주소 스택 ✗
GOT 데이터 섹션 ✗
함수 포인터 힙 포함 어디든 ✓

능력이 힙에 한정되므로 앞의 둘은 기법이 어려워서가 아니라 손이 닿지 않아서 탈락한다. 남은 건 함수 포인터고, 루프 안에 정확히 그것이 있다.

call rax — 일반 호출(call 0x401052 <make_container>)과 달리 주소가 명령어에 박혀 있지 않다. 함수 포인터 호출의 모양이고, disass main 전체에서 이것 하나뿐이다. 그리고 +317이 +167로 되돌아오므로 매 루프마다 실행된다.

세 조건이 모두 맞는다 — 함수 포인터다 / new로 힙에 있다 / 루프마다 호출된다.

2. 측정 — 소스로 알 수 없는 숫자 하나

남은 미지수는 dest 버퍼에서 menu->fp까지의 거리뿐이다. 힙 주소는 런타임에 정해지므로 여기서 디버거를 켠다.

fp의 자리는 +171 실행 직전의 rax다. (+171이 실행되면 rax가 fp 값으로 덮인다.)

출발점은 copy_container의 두 번째 인자(rsi = &dest)에서 읽는다.

vector<int>&는 참조라 rsi는 스택의 구조체 주소이고, 첫 멤버 _begin이 힙을 가리킨다. (x/3gx $rsi 하면 _begin, _end, _cap_end 셋이 보인다.)

세 청크가 전부 0x20인 이유는 요청 크기가 모두 24바이트 이하이기 때문이다. malloc(12), operator new(8) 모두 x86-64 최소 청크 0x20으로 올림된다. 그래서 src → dest → menu가 32바이트 간격으로 나란히 깔린다.

3. 인덱스 환산

std::copy는 int(4바이트) 단위로 쓴다.

그런데 fp는 8바이트, 칸은 4바이트다. 두 칸이 필요하다.

dest[9]까지 쓰려면 dest[0]부터 10개 → src.size() = 10.

4. 제약

  • dest는 resize하지 않는다. capacity가 3뿐이라 키우면 재할당이 일어나 dest가 menu 옆자리를 떠난다. std::copy는 어차피 dest 경계를 보지 않으므로 키울 이유도 없다.
  • dest[4]~dest[7]은 menu 청크의 헤더(prev_size=0, size=0x21)다. 선형 쓰기가 반드시 통과하므로 dest[6] = 0x21로 원본을 복원해 둔다. copy 직후 바로 menu->fp()가 호출되어 사이에 malloc/free가 끼지 않으므로 뭉개도 대개 동작하지만, 복원해두면 확실하다.
  • 리틀엔디안: 0x401041은 상위 4바이트가 0이라 dest[8] = 0x401041, dest[9] = 0.
  • 입력 개수를 정확히 맞춘다. make_container는 begin()~end()를 돌므로 쓰는 개수가 현재 size로 고정이다. 하나라도 더 보내면 그 숫자를 다음 cin >> selector가 먹어 메뉴가 꼬인다.
  • C++ 심볼은 맹글링된다. e.symbols["getshell"]은 KeyError다. 실제 이름은 _Z8getshellv.
  • 덮은 뒤 메뉴 프롬프트가 나오지 않는다. menu->fp가 print_menu가 아니게 되므로, sendlineafter("[*] select menu: ")로 기다리면 영원히 블록된다. copy() 다음은 바로 interactive().

5. 순서

Final Payload or Solver

로컬 실행 결과. 원격은 상단의 process를 문제 페이지에서 받은 remote(HOST, PORT)로 바꾸면 된다.

정리

처음에 checksec 표만 보고 세운 계획은 “카나리 leak → ROP → GOT overwrite”였다. 셋 다 쓰지 않았다.

보호 기법 표는 무엇이 취약한지 알려주지 않는다. 경로를 정한 뒤에 “이 경로에 무엇이 걸리는지”를 읽는 참고표다. 순서를 뒤집으면 — 소스에서 버그를 찾고, 버그를 능력 한 문장으로 번역하고, 그 능력이 닿는 곳에서 타겟을 고르고, 마지막에 표를 읽으면 — 네 항목 중 셋이 무관하고 하나(No PIE)가 선물이라는 게 보인다.

그리고 이 문제의 본론은 결국 “힙은 일렬로 깔린 메모리다” 하나다. 기법 이름을 꺼낼 필요가 없었다. 0x20 간격을 직접 세어본 게 전부다.
