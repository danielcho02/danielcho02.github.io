amounts[](증감 단위)를 스스로 덮어써 임의 쓰기를 증폭 → 단일 연결 2라운드로 ASLR 우회 → COPY-reloc된 stdin 포인터로 one_gadget 없이 결정적 셸.

Vulnerability & Code Analysis

보호기법 값
PIE No PIE (0x400000 고정)
RELRO Partial (.got.plt 쓰기 가능)
NX on
Canary 없음
IBT / SHSTK Enabled (CET)

Interpret는 입력을 고정 단어로 파싱해 동작을 실행하는 작은 인터프리터다.

단어 동작
holymoly/rolypoly/monopoly/guacamole amounts[0..3]만큼 ptr 또는 val +=
robocarpoli/halligalli/broccoli/bordercollie 같은 단위로 -=
blueberry write(1, ptr, 8) — 8바이트 leak
cranberry *ptr = val — 8바이트 임의 쓰기
mystery ptrval_switch 토글 (증감이 ptr/val 중 어디에 적용될지)

즉 primitive는 “ptr/val을 amounts[] 단위로만 증감시키는 임의 읽기/쓰기” 다.

Exploit / Solver Strategy

1. amounts 자기증폭

scanf("%48878s") → 명령어는 최대 ~6,000개뿐. 단순 누적으로는 ptr/val을 수천만까지밖에 못 만든다. 하지만 amounts[]가 **쓰기 가능한 .data**에 있으므로 증감 단위 자체를 cranberry로 키울 수 있다.

  1. ptr을 &amounts[0](0x404060, 저주소라 금방 도달)로 이동
  2. val을 키워 cranberry로 amounts[0]에 씀 → 이후 holymoly 한 번이 훨씬 큰 값을 더함
  3. 자리수별로 반복(×16 Horner)하면 수백 번 명령으로 64비트 val 완성

함정 두 가지:

  • *ptr=val은 8바이트라 amounts[0]에 쓰면 amounts[0](하위)+amounts[1](상위)이 동시에 바뀐다.
  • Increase()가 amounts[i]를 signed int32로 읽어서, 증폭값이 2³¹을 넘으면 부호가 뒤집혀 증가가 감소가 된다 → 중간 amounts[0]는 항상 < 2³¹로 유지(V//16 < 2²⁸).

val만 증폭되고 ptr은 안 된다. val은 amounts[0]에 자기 자신을 써서 ×16으로 불릴 수 있지만, ptr은 amounts[i]를 더하는 선형 증가(최대 2³¹/step)뿐이다. 그래서 쓸 수 있는 주소는 LOW(바이너리 0x404xxx)뿐 — 이게 finisher를 결정한다.

2. GOT leak + 단일 연결 2라운드 (ASLR 우회)

calloc 등의 GOT는 Interpret 전에 이미 실제 libc 주소로 resolve돼 있다. ptr을 &GOT[calloc]로 옮기고 blueberry로 리크. 그런데 scanf가 입력을 다 받은 뒤 해석을 시작하므로, 같은 payload 안에서 그 리크값을 쓸 수 없다(블라인드 단일 샷). ASLR도 매 연결 랜덤이라 2연결 방식 불가.

→ 한 연결 안에서 main을 재진입시킨다: GOT[puts]를 main(No-PIE 고정 0x4011f6, endbr64 시작)으로 덮으면, Interpret 종료 시 puts@plt가 main으로 점프 → Init(ptr/val만 리셋, amounts/switch 유지) → scanf가 한 번 더(= 라운드2). 같은 연결이라 libc_base 동일 → 라운드1에서 받은 리크로 라운드2를 만든다.

3. one_gadget이 전부 죽는 이유

libc를 디스어셈블해 확인한 결과 4개 후보 전부 불가능:

gadget 실제 호출 필요 조건 우리 호출부
0xe3b04 execve("/bin/sh", RSI, RDX) RSI·RDX NULL RDX ≠ 0 (write=8, memcmp=len−1, setvbuf=2)
0xe3b01 execve("/bin/sh", R15, RDX) R15·RDX NULL 〃 RDX
0xe3bf0 execve("/bin/sh", R15, R12) [R15]·[R12] NULL main 진입 시 __libc_csu_* 포인터 → 실패
0x107cba posix_spawn 내부 완성된 스택프레임 blind 점프로 세팅 불가

게다가 §1처럼 libc 쓰기 자체가 불가(ptr가 libc 주소에 못 감)라 __malloc_hook·FSOP도 전부 탈락. GOT 재지정 = “현재 레지스터로 함수 호출” 한 방뿐이고 그중 먹는 게 없다.

4. Finisher — COPY-reloc된 stdin 포인터 → system

돌파구는 바이너리 자신에 있었다. No-PIE 바이너리가 stdin/stdout/stderr를 참조하면 링커가 COPY 재배치로 그 FILE* 값을 바이너리 .bss에 복사한다. Init의 첫 동작:

setvbuf(stdin, …)의 RDI가 *(0x404090)에서 로드되는데 이 포인터가 LOW .bss라 덮어쓸 수 있다. 라운드2에서 두 번만 쓰면 끝:

  1. *(0x404090) = libc "/bin/sh" 주소
  2. GOT[setvbuf] = system

→ 다음 루프의 Init()에서 가장 먼저 실행되는 setvbuf(stdin, …)이 그대로 system("/bin/sh"). printf 프롬프트보다 앞이라 바로 셸. system은 함수 엔트리(endbr64)라 IBT가 강제돼도 안전하고 RDI 하나만 맞으면 되니 RDX/R12/R15 제약이 전무 → 결정적.
