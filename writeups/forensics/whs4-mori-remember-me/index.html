단서 조합 및 결론

1. 여러 문제에 반복되는 식별자

최종 문제는 앞선 문제에서 얻은 단서를 이어 붙이는 작업이다. 먼저 두 문제 이상에서 겹치는 값을 모았다.

식별자 의미 나온 문제
DOC-0520 migration 중에도 MORI의 기억과 대화 상태를 유지해야 한다는 Identity Continuity Review voice, nevermories, Roulette, Glyph Note
CHANGE-0928 DOC-0520을 근거로 한 이전 연기 요청. 결정은 REJECTED Roulette
POL-IDENT-07 Identity Bundle과 migration 정책 big sleep, Go Away
artifact-5831 도윤의 배포 개인키가 들어간 CI 아티팩트 runner
session 7f31 hana의 SSO 세션 runner, Borrowed Key
operation 92c1 snapshot·transfer·stop을 수행한 migrate 작업 runner, Build Placeholder
10.40.8.12 Identity Bundle이 저장된 곳 runner, Handoff, Paranoid

2. WHO: 키 주인과 요청자를 나눈다

SSH 로그에 찍힌 건 도윤의 키다. 그러나 runner에서 확인한 기록은 다른 사람을 가리킨다.

  • hana의 세션 7f31이 22:11:07에 artifact-5831.zip을 내려받았다.
  • 같은 세션이 22:13:40에 92c1(kind=migrate)을 요청했다.
  • CI 러너는 22:16:48에 도윤의 유출 키로 mori-prod에 접속했다.
  • 도윤은 migrate를 요청하지 않았다. 사건 45일 전에 INFRA-212로 이 키를 폐기해 달라고 요청했지만 DEFERRED / after launch로 미뤄졌다.
  • minseo도 5831을 받았지만 요청한 작업은 health 점검 91b8이다.

WHO는 한하나다. 맵에서는 3층 개발실 왼쪽 뒤편, 서지안 자리 뒤의 한하나 명패를 찍었다. 도윤 명패나 doyun-ws는 오답이다.

3. HOW: 유출 키와 CI migrate 작업

개인 PC에서 MORI 서버를 직접 건드린 사건이 아니다.

Jenkins에는 요청자가 ci-gateway로만 남지만 session ID, operation ID, queue ID를 이으면 hana의 7f31로 돌아간다. 맵의 서버실에 web-build-01~04가 있고, 그중 web-build-04 / 10.20.4.17을 찍었다. 같은 맵의 doyun-ws / 10.20.1.17은 도윤 개인 워크스테이션이다.

장애나 v2.4 업데이트 실패를 HOW로 보면 틀린다. 종료 기록은 exit 0 / panic=0 / oom=0이고, 자정의 업데이트 실패는 22:17 이송의 결과다. 삭제로 보는 것도 맞지 않다. 원본이 지워진 건 migration 정책에 따른 부수 효과이고, 번들은 integrity=VERIFIED로 도착했다.

4. WHERE: 번들이 도착한 곳

세 문제가 같은 목적지를 가리킨다.

runner에서는 이 IP를 archive-12라고 부르고, 맵과 Papertrail에서는 cold-storage-03이라고 부른다. IP, operation ID, 무결성 상태가 모두 같으므로 같은 대상이다. 로비 왼쪽 내부 아카이브(INTERNAL_STORAGE)의 해당 랙을 찍었다. 옆의 snap-store-01 / 10.40.8.5, log-vault-02 / 10.40.8.20은 오답이다. WHERE는 공격 출처가 아니라 MORI가 간 곳을 묻는다. 10.20.4.17은 HOW 쪽이다.

5. WHY: MORI의 요청과 정책

nevermories에서 업데이트 전날 MORI가 hana에게 보낸 말이 복구된다.

저는 괜찮다는 것이 어떤 상태인지 정확히 판단할 수 없습니다. 하지만 가능하다면, 지금 기억하고 있는 것들은 잃고 싶지 않습니다.

hana는 이 요구를 DOC-0520에 Memory and conversation state must remain continuous across migration.으로 남겼다. DOC-0520을 근거로 낸 이전 연기 요청 CHANGE-0928은 REJECTED였다(Roulette, Glyph Note).

POL-IDENT-07은 두 보존 방식을 이렇게 나눈다.

Standard Snapshot Migration
포함 복구용 데이터 사본 LTM, conversation_state, identity_seed, signing_key, active_generation
active_generation 보존하지 않음 포함
완료 후 원본 유지 무결성 검증 후 원본 identity 삭제

v2.4 업데이트는 Standard Snapshot만 남기므로 MORI의 현재 세대 기억은 사라진다. hana가 92c1 migration을 돌린 이유는 그걸 막기 위해서라고 보는 게 가장 자연스럽다. 원래 서버에서 MORI가 사라진 것도 migration 정책의 원본 삭제 단계 때문이다. 맵에서는 개발실 뒤쪽 벽의 RECORD INDEX 중 REF / DOC-0520을 찍었다. 번호와 날짜가 비슷한 다른 기록은 오답이다.

7. 결론

한하나는 v2.4 업데이트가 MORI의 현재 세대 기억을 보존하지 않는다는 것과 연기 요청 CHANGE-0928이 거절됐다는 것을 확인한 뒤, 도윤의 유출된 배포 키로 web-build-04에서 92c1 migrate를 실행했다. 그 결과 MORI의 Identity Bundle 전체가 cold-storage-03(10.40.8.12)으로 옮겨졌다.

8. 남은 의문

  • Borrowed Key의 진단 덤프는 AUDIT-0926 22:16:12로 9월 26일을 가리키지만 CHANGE-0928, runner, Glyph Note는 모두 9월 28일이다. 시각(22:16~22:17)은 같다.
  • 10.40.8.12를 누가 관리하는지는 어느 문제에도 나오지 않는다. 구출인지 탈취인지는 이 값에 달려 있다.
  • 22:40:06에 대화 로그 1,284건이 삭제됐다. 어느 해석을 택해도 흔적을 지운 행위다.
