요약

항목 내용
영향 버전 iowow 1.7.0, 1.7.1
수정 버전 1.7.2
위치 src/json/iwjbl.c, _jbl_create_node()
종류 CWE-590 힙이 아닌 메모리 해제, CWE-415 이중 해제
공격 조건 외부에서 받은 binn 문서를 패치하거나 DOM으로 바꿀 때
CVSS 3.1 기준 6.2 (AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H)
CVE 요청됨, 배정 대기

_jbl_create_node()는 호출한 쪽이 iwpool을 넘기면 노드를 풀에서 받는다. 그런데 에러가 나면 풀 여부와 상관없이 free()로 노드를 지운다. 풀이 준 포인터는 malloc이 준 게 아니라서 이 free()는 잘못된 해제가 되거나 나중에 풀이 정리될 때 이중 해제가 된다.

원인

src/json/iwjbl.c (1.7.1):

iwpool_alloc()은 범프 할당자다. 풀이 잡아 둔 덩어리에서 커서를 앞으로 밀고 그 자리를 돌려준다. 그래서 n은 대개 덩어리 한가운데를 가리키고 여기에 free()를 부르면 glibc는 malloc이 준 적 없는 주소라고 판단한다. n이 마침 덩어리 시작에 놓이면 그 자리에서는 해제가 되지만 iwpool_destroy()가 같은 덩어리를 한 번 더 해제한다.

에러 경로로 들어가는 데 손상된 입력은 필요 없다. BINN_TYPE_BLOB은 binn 형식에 정식으로 있는 타입이고 binn-c의 binn_create_blob()이 만들며 로드할 때도 검증을 통과한다. 그런데 위 switch에는 blob을 처리하는 case가 없다. 문자열 복사(iwpool_strndup())가 실패할 때도 같은 free()로 간다.

이 모양이 실수라는 건 같은 모듈 안에서 보인다. iwjser.c의 _jbl_json_create_node()도 똑같이 ctx->pool이 있으면 풀에서, 없으면 malloc으로 노드를 받는다. 그리고 해제할 때는 두 번 다 if (!ctx->pool)로 막는다(iwjser.c:423, :434). iwjbn.c의 노드 생성자들도 같은 조건을 건다. 2026-10-18 binn-c로 JSON 모듈을 다시 짠 커밋 c625e64에서 이 조건이 빠진 곳은 _jbl_create_node() 하나였다.

재현

binn-c 함수만으로 만든 문서다. 4바이트 blob 하나가 든 리스트이고 9바이트다.

호출은 평범하다. jbl_patch_from_json()이 풀을 안에서 만들기 때문에 호출하는 쪽이 특별한 일을 하지 않아도 풀 경로를 탄다.

ASan 결과:

1024바이트 풀 덩어리 안 464바이트 지점을 해제하려 했다. 새니타이저 없이 빌드해도 glibc가 잡고 프로세스를 끝낸다(exit 134). 노드가 놓인 위치에 따라 메시지가 다르다.

영향받는 공개 API는 이렇다.

API 풀 결과
jbl_patch_from_json() 안에서 생성 잘못된 해제
jbl_merge_patch() 안에서 생성 이중 해제
jbl_to_node(…, pool) 호출자가 전달 잘못된 해제 또는 이중 해제
jbl_to_node(…, 0) 없음 영향 없음

wrap=true로 로드해도 똑같이 재현된다.

한계

  • 입증한 건 서비스 거부까지다. glibc가 두 경우를 모두 잡고 abort한다. 이런 검사가 없는 할당자에서는 힙 메타데이터가 망가질 수 있지만 그 이상은 확인하지 않았다.
  • 원격 공격 경로는 iowow 안에 없다. iowow는 라이브러리다. 외부에서 받은 binn 문서를 jbl_create_from_buf()로 읽고 패치하거나 DOM으로 바꾸는 애플리케이션이 영향을 받는다. 그래서 CVSS는 AV:L로 매겼다.
  • EJDB2까지는 따라가지 않았다. EJDB2는 1.7.0을 고정해서 쓰고 저장된 문서에 jbl_to_node(…, pool)을 호출한다. 다만 그 문서가 어디서 채워지는지는 확인하지 못했다.

패치

upstream 수정은 54e83fc이고 보고서에 붙인 패치와 같은 조건이다. 풀이 있으면 노드를 해제하지 않는다.

회귀 테스트 jbl_test1_14도 같이 들어갔다. 위의 9바이트 문서를 binn-c로 직접 만들고 두 로드 모드에서 패치 API 세 개와 jbl_to_node()가 JBL_ERROR_CREATION을 돌려주는지 확인한다.

제보 과정

10월 23일 오후 4시 반쯤 GitHub의 비공개 취약점 제보로 보냈다. 메인테이너는 4시간 만에 받아들였고 13분 뒤 master에 수정을 올렸다. 1.7.2는 10월 30일에 나왔다.

그 뒤 advisory는 2주 동안 draft로 남아 있었다. 나는 advisory 상태만 보고 답이 없다고 생각했는데, 커밋 기록을 보니 이미 고쳐져 있었다. 원인은 advisory 페이지에 있었다. 메인테이너가 advisory용 임시 비공개 포크에 PR을 열었다가 master에 직접 커밋했고 그 PR이 열린 채로 남아 있었다. GitHub는 이런 PR이 있으면 advisory를 공개하지 못하게 막는다.

11월 6일 늦게 확인해서 미안하다는 말과 함께 이 사정을 댓글로 알렸다. 이틀 뒤 advisory가 공개됐고 CVE 요청도 들어갔다.

조용히 고치고 서류를 안 하는 메인테이너라고 넘겨짚을 뻔했다. 답이 없어 보이면 먼저 커밋 기록과 advisory 타임라인부터 볼 생각이다.
